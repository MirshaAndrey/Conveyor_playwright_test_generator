## 1. Обзор

Conveyor — CLI-инструмент на Go для автоматической генерации, запуска и починки E2E-тестов (Playwright + TypeScript). Инструмент использует большие языковые модели (LLM) для создания production-ready тестового кода на основе текстовых описаний тест-кейсов.

Conveyor поддерживает три провайдера LLM: **Ollama** для полностью локальной работы без передачи данных в облако, **Google Gemini API** и **Anthropic Claude API** для облачной генерации с максимальным качеством.

Ключевая особенность — агентный режим, реализующий полный цикл автоматизации: сканирование страницы, генерация теста, ревью кода, запуск, автоматическая починка при падении и рефакторинг под Page Object Model.

### 1.1. Ключевые возможности

- **Три провайдера LLM:** Ollama (локально), Google Gemini API, Anthropic Claude API
- **Четыре режима работы:** интерактивный, одиночный, пакетный (TXT/JSON), агентный
- **Автосканирование страниц:** DOM-элементы (data-testid, aria-label, кнопки, поля) и перехват API-запросов (XHR/fetch)
- **Generator → Reviewer:** двойной LLM-проход для повышения качества кода
- **Валидация + Retry:** автоматическая проверка наличия `test.describe`, `expect()`, отсутствия `waitForTimeout`
- **Fix Loop:** при падении теста LLM анализирует ошибку Playwright и исправляет код автоматически (до N попыток)
- **Post-batch POM:** рефакторинг всех тестов под Page Object Model после генерации
- **Перехват сети:** сканер собирает XHR/fetch-запросы, фильтрует аналитику, дедуплицирует
- **Умное сохранение:** файлы группируются по разделам с транслитерацией кириллицы

## 3. Провайдеры LLM

Conveyor поддерживает три провайдера для генерации тестов. Выбор задаётся флагом `-provider`, полем `provider` в `config.json`, или интерактивно при запуске без аргументов.

### 3.1. Ollama (локально)

Полная приватность — данные не покидают машину. Требуется установленный и запущенный сервер Ollama.

```bash
./conveyor -provider ollama -model qwen2.5-coder:7b
```

При запуске без флага `-model` Conveyor запросит список установленных моделей у сервера Ollama и предложит выбор в интерактивном меню.

### 3.2. Google Gemini API

Облачный провайдер от Google. API-ключ передаётся через флаг `-key` или переменную окружения `GEMINI_API_KEY`.

```bash
./conveyor -provider gemini -key "AIzaSy..."
GEMINI_API_KEY="AIzaSy..." ./conveyor -provider gemini
```

Модель по умолчанию: `gemini-2.5-flash`. Бесплатный тариф: между запросами автоматически добавляется пауза 3 секунды для соблюдения rate limit.

### 3.3. Anthropic Claude API

Облачный провайдер от Anthropic. API-ключ передаётся через флаг `-key` или переменную окружения `ANTHROPIC_API_KEY`.

```bash
./conveyor -provider claude -key "sk-ant-..."
ANTHROPIC_API_KEY="sk-ant-..." ./conveyor -provider claude
```

**Доступные модели Claude:**

| Модель | Описание | Рекомендация |
|--------|----------|--------------|
| `claude-sonnet-4-6` | Баланс качества и скорости | По умолчанию, рекомендуется |
| `claude-opus-4-6` | Максимальное качество | Сложные/критичные тесты |
| `claude-haiku-4-5-20251001` | Самый быстрый | Массовая генерация |

### 3.4. Приоритет настроек

Conveyor применяет настройки в следующем порядке (от высшего приоритета к низшему):

1. CLI-флаги: `-key`, `-model`, `-provider`
2. Переменные окружения: `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`
3. Файл конфигурации `config.json`
4. Встроенные значения по умолчанию

## 4. Режимы работы

### 4.1. Интерактивный режим

Запуск без аргументов. Программа предложит выбрать провайдера и модель, затем ожидает ввод тест-кейсов в консоли. Ответ LLM стримится в реальном времени.

```bash
./conveyor
```

### 4.2. Одиночный режим

Генерация одного теста по описанию из командной строки.

```bash
./conveyor -task "Авторизация с неверным паролем: ошибка"
```

### 4.3. Пакетный режим — JSON (рекомендуется)

Массовая генерация из структурированного файла `cases.json`. Тесты сохраняются в подпапки по разделам (`section`).

```bash
./conveyor -cases-file cases.json
```

### 4.4. Пакетный режим — TXT

Простой список задач, по одной строке на файл. Сохраняется без подпапок.

```bash
./conveyor -tasks-file cases.txt
```

### 4.5. Режим с ревью (Generator → Reviewer)

После генерации каждого теста запускается второй LLM-проход. Reviewer проверяет код по блокам: покрытие задания, запрещённые паттерны, качество селекторов, структура.

```bash
./conveyor -cases-file cases.json -review
```

### 4.6. Режим со сканированием

Перед генерацией Conveyor сканирует указанную страницу через headless Chromium и собирает DOM-элементы и API-запросы. Результат подставляется в промпт.

```bash
./conveyor -cases-file cases.json -scan-url https://app.example.com/login
```

## 5. Агентный режим

Агентный режим — полностью автоматический pipeline. Для каждого тест-кейса из `cases.json` выполняется цепочка: сканирование страницы (если задан `url`), генерация теста с retry при невалидном ответе, опциональное ревью, запуск через Playwright, и автоматическая починка при падении (до N итераций).

### 5.1. Pipeline агента

```
SCAN → GENERATE → REVIEW → TEST → FIX LOOP → POM
```

| Этап | Описание |
|------|----------|
| **SCAN** | Если у кейса задан `url`, сканируется страница (DOM + сетевые запросы) |
| **GENERATE** | LLM генерирует тест. При ошибке валидации — retry (до `max_retries` раз) |
| **REVIEW** | (если `-review`) Второй LLM-проход проверяет и исправляет код |
| **TEST** | `npx playwright test` запускает сгенерированный файл |
| **FIX LOOP** | При падении теста LLM получает текст ошибки и исправляет код (до `-max-fix` попыток) |
| **POM** | (если `-pom`) После всех кейсов все тесты отправляются на рефакторинг под Page Object Model |

### 5.2. Команды запуска

```bash
# Базовый агентный режим
./conveyor -agent -cases-file cases.json

# С ревью и POM-рефакторингом
./conveyor -agent -cases-file cases.json -review -pom

# Увеличить число попыток починки
./conveyor -agent -cases-file cases.json -max-fix 5

# Только генерация без запуска тестов
./conveyor -agent -cases-file cases.json -no-run

# С Claude в качестве провайдера
./conveyor -agent -cases-file cases.json -provider claude -key "sk-ant-..."
```

### 5.3. Индикаторы трекера

| Иконка | Цвет | Статус |
|--------|------|--------|
| `[ ]` | Серый | Ожидает выполнения |
| `[⊕]` | Фиолетовый | Сканирование страницы |
| `[~]` | Жёлтый | Генерация теста |
| `[»]` | Голубой | Ревью кода |
| `[►]` | Синий | Запуск теста |
| `[↻]` | Жёлтый | Исправление ошибки (N/M) |
| `[+]` | Зелёный | Готово |
| `[x]` | Красный | Ошибка |

## 6. Сканер страниц

Conveyor включает встроенный headless-сканер на базе Playwright. Сканер собирает два типа данных: DOM-элементы страницы и сетевые API-запросы.

### 6.1. DOM-элементы

- Все `data-testid` атрибуты с тегом, типом, текстом и признаком видимости
- `aria-label` атрибуты с тегом, ролью и счётчиком вхождений
- Кнопки: `button`, `[role=button]`, `input[type=submit]`, `input[type=button]`
- Поля ввода: `input`, `textarea`, `select` с `label`, `placeholder`, `name`, `id`, `testid`
- Для `<select>` — список доступных опций (до 20 значений)
- Ссылки: до 30 элементов `a[href]` с текстом (только видимые)
- Заголовки: `h1`, `h2`, `h3` с текстом

### 6.2. Готовые Playwright-локаторы

`formatScanContext` выдаёт LLM не сырые атрибуты, а готовые локаторы по приоритету:

```
getByTestId(...)  >  getByRole(...)  >  getByLabel(...)  >  getByPlaceholder(...)  >  locator('[name=...]')  >  locator('#id')
```

Элементы с дубликатами (`count > 1`) автоматически получают `.first()` с предупреждением:

```typescript
page.locator('[name="btnI"]').first() /* ⚠ на странице 2 таких элемента — без .first() будет strict mode violation */
```

### 6.3. Перехват API-запросов (XHR/fetch)

Сканер подписывается на события `request` и `response` **до** навигации на страницу, что гарантирует перехват всех запросов, включая инициализацию SPA. Собираемые данные:

- HTTP-метод (GET, POST, PUT, DELETE)
- Полный URL и нормализованный путь
- HTTP-статус ответа (200, 401, 404 и т.д.)
- Признак наличия тела запроса (для POST/PUT/PATCH)

**Фильтрация и дедупликация:** запросы к доменам аналитики и трекинга автоматически исключаются (Google Analytics, GTM, Facebook, Hotjar, Sentry, Clarity, DoubleClick и другие). Одинаковые запросы дедуплицируются по ключу `метод + нормализованный URL`. При нормализации сохраняются параметры фильтрации (`page`, `sort`, `filter`, `q`, `search`), случайные параметры (`token`, `timestamp`) удаляются.

### 6.4. Как работает сканер

1. Встроенный JS-скрипт записывается во временный `.js` файл в CWD (рядом с `node_modules`)
2. Запускается через `node` с `NODE_PATH` указывающим на `node_modules`
3. Подписка на события `request` и `response` **до** вызова `page.goto()`
4. Playwright открывает страницу с `waitUntil: networkidle`
5. DOM-данные извлекаются через `page.evaluate()`
6. DOM и сетевые данные мержатся в единый JSON-объект
7. Результат форматируется в текстовый контекст и подставляется в промпт LLM
8. Временный файл удаляется

## 7. Конфигурация

### 7.1. Файл config.json

Опциональный файл конфигурации. Расположение задаётся флагом `-config` (по умолчанию `config.json` в текущей директории). Рекомендуется добавить в `.gitignore`, так как файл может содержать API-ключи.

```json
{
  "provider": "claude",
  "claude_api_key": "sk-ant-...",
  "claude_model": "claude-sonnet-4-6",
  "context": "Описание тестируемого приложения",
  "review_mode": true,
  "max_retries": 3
}
```

### 7.2. Поля конфигурации

| Поле | По умолчанию | Описание |
|------|-------------|----------|
| `provider` | `ollama` | Провайдер LLM: `ollama`, `gemini` или `claude` |
| `gemini_api_key` | (пусто) | API-ключ Google Gemini |
| `gemini_model` | `gemini-2.5-flash` | Модель Gemini |
| `claude_api_key` | (пусто) | API-ключ Anthropic Claude |
| `claude_model` | `claude-sonnet-4-6` | Модель Claude |
| `ollama_url` | `http://localhost:11434` | Адрес сервера Ollama |
| `ollama_model` | `mistral-small3.2:latest` | Модель Ollama |
| `context` | (пусто) | Описание приложения — подставляется в `{{context}}` |
| `system_prompt` | встроенный | Полная замена системного промпта |
| `review_mode` | `false` | Включить Reviewer для всех запусков |
| `max_retries` | `2` | Повторов при ошибке валидации ответа LLM |

### 7.3. Формат cases.json

```json
[
  {
    "section": "auth",
    "name": "login_valid",
    "task": "Авторизация с валидными кредами: успешный вход, редирект на дашборд",
    "url": "https://app.example.com/login",
    "prompt_hint": "Форма: поле email (#email), поле password (#password), кнопка Submit"
  }
]
```

| Поле | Обязательное | Описание |
|------|-------------|----------|
| `section` | Да | Раздел — создаёт подпапку `TestCasesTS/<section>/` |
| `name` | Да | Короткое имя для трекера и имени файла |
| `task` | Да | Полное описание задачи — уходит в промпт LLM |
| `url` | Нет | URL для автосканирования (DOM + сетевые запросы) |
| `prompt_hint` | Нет | Ручные подсказки — дополняют результат сканирования |

## 9. Архитектура проекта

### 9.1. Структура файлов

| Файл | Назначение |
|------|------------|
| `main.go` | CLI-флаги, выбор провайдера, роутинг между режимами |
| `agent.go` | Агентный loop: scan → generate → review → run → fix → pom |
| `batch.go` | Пакетный режим, `BatchConfig`, `generateOne` (retry + review) |
| `runner.go` | Запуск `npx playwright test`, парсинг ошибок Playwright |
| `scanner.go` | Headless сканер (DOM + перехват сети), встроенный JS-скрипт |
| `prompt.go` | Системные промпты, `buildCasePrompt`, `validateContent` |
| `ollama.go` | API Ollama: `sendRequest`, `pickModel`, `checkOllama`, стриминг |
| `gemini.go` | API Gemini: `sendGeminiRequest`, SSE-стриминг |
| `claude.go` | API Claude: `sendClaudeRequest`, SSE-стриминг |
| `config.go` | `Config` struct, `loadConfig` |
| `files.go` | `TestCase` struct, `loadCasesJSON`, slug-генерация, сохранение |
| `tracker.go` | Терминальный UI: прогресс-бар, статусы, итоговая сводка |

### 9.2. Поток данных

```
cases.json
    └─► loadCasesJSON() → []TestCase
            ├─► runAgent()           (агентный режим)
            │       └─► processOneCase()
            │               ├─► runScanner()        → ScanResult
            │               ├─► formatScanContext()  → scanHint (string)
            │               ├─► generateOne()        → .ts файл
            │               ├─► runPlaywrightTest()  → RunResult
            │               └─► fixLoop()            → исправленный .ts файл
            │                       └─► buildFixPrompt(code, error, scanHint)
            └─► runBatchCases()      (пакетный режим)

doGenerate / doReview / doFix  (batch.go / agent.go)
    ├─► sendRequest()          (Ollama)
    ├─► sendGeminiRequest()    (Gemini)
    └─► sendClaudeRequest()    (Claude)
```

### 9.3. Структура выходных файлов

```
TestCasesTS/
├── <section>/
│   └── <timestamp>_<slug>.ts          # пакетный режим с cases.json
├── <timestamp>_<slug>.ts              # пакетный режим с TXT
└── pom/
    ├── pages/
    │   └── <Name>Page.ts              # Page Object классы (после -pom)
    └── specs/
        └── <name>.spec.ts             # рефакторированные спецификации
```

## 10. Система промптов

### 10.1. Системный промпт генератора

**Роль:** Senior QA Automation Engineer.

**Требования к генерации:** TypeScript, Playwright Test, `test.describe` + `test`, переиспользуемый код.

**Приоритет селекторов:** `getByTestId` > `getByRole` > `getByLabel` > `getByText`.

**Запрещены:** `waitForTimeout`, `console.log`, пустые тесты, TODO, XPath, `nth-child`.

### 10.2. Промпт Reviewer

Четыре блока проверки:

1. **Покрытие задания** — каждый шаг чеклиста → действие + `expect`
2. **Запрещённые паттерны** с конкретными заменами (`waitForTimeout` → `waitFor({state:'visible'})`, `page.waitForNavigation()` → `Promise.all([page.waitForURL(...), click()])`)
3. **Качество селекторов** (XPath → `getByTestId`, CSS-классы → `getByRole`)
4. **Структура и типизация** — явные типы, нет `any`, нет `TODO`

Если найдена хотя бы одна проблема — возвращает исправленный полный файл.

### 10.3. Промпт Fix

Получает три раздела:

- `=== КОД ТЕСТА ===` — исходный TypeScript файл
- `=== ОШИБКА PLAYWRIGHT ===` — вывод упавшего теста
- `=== ДОСТУПНЫЕ СЕЛЕКТОРЫ СТРАНИЦЫ ===` — контекст сканирования (если есть)

**Правило:** использовать только селекторы из раздела сканирования, не придумывать новые. Исправлять только проблемное место, не переписывать тест целиком.

**Типовые решения по типу ошибки:**

| Ошибка | Решение |
|--------|---------|
| Timeout / not found | Взять селектор из раздела сканирования, добавить `waitFor({state:'visible'})` |
| Strict mode violation (×2) | Добавить `.first()` к локатору |
| Element hidden после `fill()` | Добавить `await input.blur()` перед `waitFor` кнопки |
| Navigation / page closed | `Promise.all([page.waitForURL(...), element.click()])` |

### 10.4. Промпт POM рефакторинга

Получает все сгенерированные тесты. Создаёт Page Object класс для каждой уникальной страницы (`readonly Locator` + методы действий). Spec-файлы используют Page Object без прямого обращения к `page`. Формат ответа: маркеры `--- FILE: path.ts ---` разделяющие файлы.

### 10.5. Валидация ответа LLM

Функция `validateContent` проверяет четыре критерия:

1. Ответ не пустой
2. Содержит `test.describe`
3. Содержит хотя бы один `expect()`
4. Не содержит `waitForTimeout`

При провале валидации запрос повторяется (до `max_retries` раз).

### 10.6. Шаблон `{{context}}`

Системный промпт поддерживает плейсхолдер `{{context}}`, который заменяется на объединение трёх источников:

1. Описание приложения из `config.json` (поле `context`)
2. Результат сканирования страницы (DOM-элементы и API-запросы)
3. Ручные подсказки из поля `prompt_hint` кейса
